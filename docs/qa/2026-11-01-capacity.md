# Concurrent-player resilience — 2026-11-01

## Delivered protections

- Handle WebSocket protocol errors on their own socket. An oversized 20 KiB
  frame previously caused an unhandled error and stopped the backend; the new
  integration test first reproduced that crash and now verifies that another
  socket and HTTP requests remain alive.
- Rate-limit incoming frames before parsing JSON, including malformed frames.
- Stop feeding a socket whose existing output backlog reaches 256 KiB. A valid
  large inbox on an empty socket is still deliverable; the backlog bound is not
  a maximum application-message size. Game, DM and challenge notifications all
  use the same transport helper. Sync/async send failures are isolated.
- Expire unidentified connections after 15 seconds and discard authentication
  results arriving after a transport has closed. Existing verified players do
  not expire. Recovery remains within the existing game reconnect contract.
- Limit total admitted WebSockets (MAX_WS_CONNECTIONS, default 1000), refusing
  additional upgrades with 503 and Retry-After while preserving existing peers.
  This is an admission bound, not a production-capacity guarantee.
- Reuse global and per-topic leaderboard snapshots until mutations invalidate
  them. Cache only the first 100 rows plus a viewer-independent rank map. Topic
  cache has 16 LRU entries; responses are cloned and each viewer gets their own
  rank. Completed games immediately invalidate the relevant rankings.
- Add authenticated aggregate runtime metrics at /admin/runtime, gated by the
  existing ADMIN_STATS_TOKEN and Cache-Control:no-store. Includes RSS/heap,
  5-second event-loop delay, connection cap, active matches, rooms and proxy
  configuration. Disabled without an admin token. No credentials/account lists
  are returned. Public /health includes acceptingConnections.

## Repeatable local measurement

Run in backend:

    node scripts/load-check.cjs 200 10000
    node scripts/load-check.cjs 500 10000
    node scripts/load-check.cjs 1000 10000

The tool always creates its own local backend and empty temporary DATA_DIR;
it does not accept a remote target. It seeds 10000 historical accounts, issues
its own signed guest tokens, identifies real WS clients, requests global/topic
leaderboards, pairs humans, plays six normally timed rounds and verifies every
answer ACK, final result, HTTP health and exactly-once persisted game count.
IPC instrumentation samples the backend process separately from the generator.
Tokens and temporary test secrets are never printed. Tests exercise graceful
flush/shutdown through explicit test-only IPC on Windows.

All runs used Node 24.19.0 on the development machine, over loopback, and 10000
historical accounts. The 1000-player run took 45 seconds and recorded peak
event-loop delay 184.55ms. Differences between runs include normal scheduling
and warmup variation; these are not controlled hardware benchmark rankings.

## Verification and boundaries

- 164 backend tests passed. Includes failing-then-passing oversized-frame,
  excess-upgrade, expired-identification, late-auth and large-inbox cases;
  cache privacy, bounded retention and immediate rank refresh are covered.
- CI=true frontend production build compiled successfully.
- Independent read-only review found the large-inbox and late-auth cases; both
  now have regressions and fixes. No remaining concrete product findings.
- Browser checks cover actual App multiplayer, connection loss and recovery,
  messaging, friends, challenges, full duel/rematch and history.

These are local authenticated WS/game workloads, not a Railway capacity
certification, long-duration soak test, Firebase load test or photo-bandwidth
test. Railway API inspection was blocked by expired connector authentication.
Do not promise 1000 production users from these measurements alone.

Before increasing production capacity, confirm actual Railway CPU/RAM limits,
metrics, persistent volume, and trusted proxy hop configuration. The current
stores and live games belong to one process: do not simply add replicas.
Multiple instances require a shared transactional database plus shared
matchmaking/presence and routing/recovery for live sessions. Raising an
admission cap is not a substitute for measuring that configuration.
