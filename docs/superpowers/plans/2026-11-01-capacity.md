# Concurrent player resilience implementation plan

**Goal:** prevent one failing client from taking down QuizzUp, measure a real
multi-player workload, and fix measured server bottlenecks without changing play.

**Architecture:** retain the current single-instance Node/WS deployment and JSON
stores for this bounded change. Protect transport resources, reuse unchanged
expensive reads, and keep load testing on isolated local stores.

**Constraints:** no production load generation, no production data migration,
no additional Railway replicas with unshared in-memory games/JSON stores, no
paid infrastructure changes. Report measured local capacity separately from
production hosting capacity. Railway connector currently requires reauthentication.

- [x] Reproduce unhandled WebSocket protocol error in a failing integration test.
- [x] Contain the error to its socket and apply input limits before JSON parsing.
- [x] Add a repeatable isolated load tool: real identification, leaderboard,
  matchmaking, six rounds, acknowledgements, results and persisted stats.
- [x] Measure latency, event-loop lag, memory and completion at increasing load.
- [x] Add regression tests and fix measured read bottlenecks and unsafe buffering.
- [x] Verify malformed peers, overload bounds, reconnection and normal gameplay.
- [x] Run backend tests, real two-player journey, frontend build and independent review.
- [ ] Publish verified code and check live health; document production limits and
  the database/shared-session work required before multi-instance scaling.
